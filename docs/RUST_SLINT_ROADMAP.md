# Migración de Photo Culler a Rust y Slint

**Objetivo.** Entregar Photo Culler con lógica de producto, catálogo, procesamiento de imagen, CLI y servidor en Rust. Una interfaz declarativa Slint se compilará para navegador con WebAssembly y para escritorio nativo. Ambas versiones usarán la misma API REST. El trabajo se divide en **64 paquetes con aceptación independiente**.

**Base integrada.** La rama `feature/rust-slint-migration` parte del PR [#24](https://github.com/scherenhaenden/photo-culler/pull/24), `bfd38e8`, que ya incorpora el PR [#25](https://github.com/scherenhaenden/photo-culler/pull/25), `cdf2b21`. El merge `9dae03e` incorpora el PR [#27](https://github.com/scherenhaenden/photo-culler/pull/27), `b2fe9e8`. Esta base conserva importación, visor, preselección, edición y control térmico legado como referencia funcional. La prueba de integración local con Python 3.14 dio **141 aprobadas y 7 E2E excluidas**, con catálogo y caché de prueba temporales. La validación en la NAS y la nueva arquitectura pertenecen a este plan.

## Arquitectura objetivo

```text
Slint nativo ── HTTP por loopback ────┐
                                      ├── REST /api/v1 ── Rust / Axum / Tokio
Slint WASM ─── HTTP mismo origen ────┘        │
                                               ├── Catálogo SQLite/WAL
CLI Rust ────── API o servicios Rust ───────────┼── Jobs persistentes
                                               └── Motor de imágenes Rust + archivos locales
```

| Componente | Responsabilidad |
|---|---|
| `photo-culler-core` existente | Identidades, decisiones, agrupación y reglas de producto. |
| `photo-culler-image-engine` existente | Decodificación, miniaturas, métricas y renderizado de recetas. Reutilizar el motor y comparador actuales como punto de partida. |
| `photo-culler-api` | Tipos Serde, errores y contratos versionados compatibles con el servidor nativo y `wasm32-unknown-unknown`. |
| `photo-culler-client` | Cliente HTTP y estado de presentación compartidos, con transporte nativo y Fetch en navegador. |
| `photo-culler-server` | API Axum, almacenamiento SQLite vía SQLx, archivos estáticos, jobs y adaptador Linux para sensores NAS. |
| `photo-culler-slint` | Componentes `.slint`, controladores Rust y entradas específicas de escritorio y WASM. |
| `photo-culler-cli` existente | Comandos operativos sobre los mismos servicios o API. Los comandos que actúen sobre un catálogo activo lo harán a través de su servidor. |

- **Web.** El servidor sirve el canvas Slint, `.wasm` y cargador generado por `wasm-bindgen` desde el mismo origen que `/api/v1`. El navegador recibe miniaturas y resultados. El servidor accede a los originales bajo raíces autorizadas. Para seguir jobs, la primera UI puede consultar snapshots REST con frecuencia adaptativa. Los eventos HTTP quedan como extensión si las pruebas de latencia y carga los justifican.
- **Escritorio.** Slint abre la ventana nativa y usa un servidor Rust en loopback, con puerto asignado por el sistema, sesión efímera y cierre coordinado. Los selectores de carpetas y la apertura de archivos son adaptadores nativos. En web se ofrecen las fuentes que el servidor ya tiene autorizadas.
- **Catálogo.** SQLite en WAL, un único propietario de escritura por biblioteca y migración sobre una copia consistente. Los identificadores, estados de decisión, relaciones RAW/JPEG y recetas existentes forman parte del contrato de compatibilidad. La cancelación y los reintentos se verifican al nivel de transacciones, jobs y archivos derivados.
- **Procesamiento.** Rust reutiliza métricas existentes y valida la decodificación RAW por cámara y formato. Un códec nativo empaquetado solo se considera si supera las pruebas de cobertura y distribución. La preselección se explica y se puede revertir. El usuario aprueba el exportado y los derivados tienen una raíz de salida explícita.
- **Límite de Slint en navegador.** Slint renderiza en canvas mediante WebGL. Su documentación indica que el canvas no ofrece accesibilidad para lectores de pantalla. La prueba temprana verificará teclado, foco, escala y rendimiento en navegador. El alcance de accesibilidad de la entrega web se decide con esa evidencia antes del corte. [Slint para web](https://docs.slint.dev/latest/docs/slint/guide/platforms/web/)

## Cómo arrancan las 64 tareas a la vez

**Preparación común, una sola vez.** El integrador prepara un commit de arranque sobre esta rama antes de asignar implementaciones. Contiene el workspace mínimo, las interfaces congeladas que consumen los paquetes, un servidor REST simulado, fixtures, y un ejecutor que compila cada entrega en un workspace temporal. La rama actual conserva el plan y la referencia funcional. La preparación común pertenece al inicio de la implementación.

| Elemento común | Qué se congela para que los equipos puedan trabajar por separado |
|---|---|
| Identidad y datos | `GalleryId`, `SourceId`, `PhotoId`, `FileId`, `JobId`, `RecipeRevision`, cursor opaco, `DecisionState` legado, estados `online`/`offline`/`missing`, representación JPEG/RAW, hora UTC con zona o procedencia original. |
| HTTP | `/api/v1/health`, catálogo y fotos, galerías y fuentes, importación/análisis y sus jobs, decisiones, sesiones, grupos, miniaturas, recetas, exportaciones y NAS. Congelar DTOs y respuestas de ejemplo, errores `code/message/request_id`, orden estable y conflictos de revisión. La API pública anterior queda inventariada como referencia de compatibilidad. |
| Jobs | Transiciones y razones explícitas, versión monotónica del snapshot y resultado terminal. Las pausas manual y térmica se registran por separado. Las implementaciones llaman puertos ya definidos para persistencia, escaneo, métricas, reloj, sensores y entrega de archivos. |
| UI | Tokens, tamaños, acciones, nombres de estados y contratos de componentes Slint. El frontend se prueba con REST simulado, incluidas respuestas vacías, lentas, fallidas y paginadas. |
| Datos de prueba | Catálogo legado sintético con WAL, recetas y perfiles, catálogo pequeño con ráfagas y pares RAW/JPEG, faltantes y volúmenes offline, fixtures de imágenes y sensores, y catálogo sintético de 10.000 elementos. Cada muestra RAW real necesita permiso de uso y procedencia registrada. |
| Registro y toolchain | Versión de Rust y Slint fijadas, convenciones de módulos, scripts de integración y puntos de registro para rutas, repositorios, componentes y CI. Comprobar un ejemplo Rust nativo y un `wasm32` con REST simulado antes de repartir trabajo. |

**Propiedad.** Cada paquete tiene un área exclusiva. Las rutas de las tablas son relativas a `rust/`, salvo las que empiezan con `repo/`, que son relativas a la raíz del repositorio. Una prueba adicional vive en el área exclusiva o en un directorio `tests/task_NN/` del crate. La ficha `repo/migration/tasks/NN.toml` es exclusiva de esa tarea y registra imports, módulos, rutas HTTP, dependencias Cargo y comandos de prueba que el integrador debe conectar. Los paquetes individuales preparan esos datos. El integrador aplica los cambios compartidos en `Cargo.toml`, `Cargo.lock`, módulos raíz, routers, agregadores Slint y workflows. Cada persona trabaja desde el mismo commit de arranque con su checkout aislado. Las tareas pueden entregarse y revisarse en cualquier orden contra el mismo arnés.

**Prueba por paquete.** Cada entrega muestra entrada, salida y caso de error según su contrato. Si el servicio vecino todavía está en desarrollo, la prueba usa el doble común. Los cambios de contrato se solicitan al integrador con un caso reproducible. Los cambios compatibles pueden incorporarse juntos y se publica una nueva revisión del arnés solo cuando hace falta. Las pruebas sobre hardware y servidores reales se ejecutan al ensamblar los paquetes.

**Métricas de aceptación.** El plan mide integridad de catálogo y originales, concordancia con las decisiones humanas, tiempo de importación/análisis, primer acceso a miniaturas, desplazamiento, RAM pico y arranque en frío. Los valores de referencia se registrarán con commit, máquina y corpus. Los límites de aceptación se fijan antes de comparar la versión candidata en ese mismo entorno.

## Ensamblaje y entrega

El [plan de la primera demo Rust y Slint](rust-slint-demo/README.md) desglosa la etapa 1 en 34 fichas e incluye arranque nativo en macOS, Linux y Windows, además del navegador.

Las etapas siguientes ordenan **los merges de integración y las pruebas de extremo a extremo**. El trabajo de las 64 fichas ya puede estar en marcha desde el commit común. Los scripts, guías y pruebas que esperan un artefacto real se desarrollan con su sustituto y se reejecutan cuando llega el artefacto.

| Etapa | Qué se conecta | Evidencia para avanzar |
|---|---|---|
| 1. Primer recorrido vertical | REST y los dos arranques Slint con una galería simulada y una miniatura. | Compila `wasm32`, el navegador usa el mismo origen, el escritorio abre y cierra, y se documenta el alcance de accesibilidad web. |
| 2. Catálogo y medios | SQLite, migración, fuentes, importación, decodificación y miniaturas. | Se abre una copia migrada, conserva IDs y decisiones, se reanuda una importación interrumpida y se recupera una fuente offline. |
| 3. Sesión completa | Jobs, métricas, grupos, preselección, recetas, CLI y UI Slint. | El corpus cumple umbrales acordados y navegador/escritorio completan la misma sesión con decisiones persistidas y derivados separados. |
| 4. Distribución y corte | Artefactos, documentación comprobada, NAS y restauración. | Pasan las pruebas sobre instalaciones limpias y NAS de prueba. Se documentan límites por formato y plataforma y se ensaya volver a la copia anterior. |

**Salida de la migración.** El binario Rust y los clientes Slint son los puntos de entrada soportados. Se verifica la paridad de las funciones inventariadas en la tarea 01, un catálogo legado se migra y restaura, una sesión se completa en ambos clientes y se incluyen instrucciones y licencias en los artefactos. El integrador cambia las entradas de build y release y retira los lanzadores Python, HTMX, egui y Tauri tras aprobar el corte. Se conserva un commit de referencia para reproducir el comportamiento anterior. Las ampliaciones de selección editorial con diversidad y restauración por IA siguen en la [hoja de ruta de producto](FUTURE_INTELLIGENT_WORKFLOW.md).

**Secuencia de datos para el corte.** Detener escrituras, tomar y comprobar una copia consistente, migrar esa copia, validar identidades, referencias y conteos, y abrir el servicio nuevo con la copia validada. La vuelta atrás restaura el último catálogo compatible documentado e informa qué decisiones se hicieron después del cambio de escritor. Los originales mantienen sus rutas y hashes durante el ensayo.
