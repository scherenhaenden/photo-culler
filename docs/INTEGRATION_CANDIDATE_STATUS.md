## Cambios recientes aún sin aceptar

- **Importación:** smoke pequeños aceptaron movimiento inequívoco, identidad separada para ruta reutilizada/duplicado, exclusión parcial, persistencia y reescaneo repetido. Un smoke aceptó SIGKILL/restart/resume con manifest completo y 100/12.000 observaciones ya confirmadas; terminó en 12.000 filas/IDs únicos. Otro smoke interrumpió manifest parcial en 256 entradas y terminó en 20.000 filas `files` y `photos`; en el catálogo nuevo usado, el esquema `UNIQUE NOT NULL` implica 20.000 IDs distintos, aunque no hubo `COUNT(DISTINCT)` directo. La migración v9 añade índice único a catálogos legacy y revierte ante IDs duplicados o null/vacíos. El arreglo SQL rechaza aún movimientos ambiguos. Pairing, rutas múltiples, contención concurrente, benchmark 10k y catálogos reales siguen sin aceptación.
- **Library/import UI:** callbacks visibles anterior/siguiente con cursor y estado/contador; errores de carga dejan la página actual utilizable; decisiones masivas se restringen a selección visible bajo filtros. Los fallos al programar localmente la carga de fuentes, estimación o control de trabajo ahora liberan el estado ocupado y muestran error recuperable. Sin aceptación runtime.
- **Metadatos:** lector acotado JPEG APP1/TIFF-EXIF (Make, Model, orientación, fechas/offset, exposición, apertura, ISO y focal); sin TIFF standalone, RAW, maker notes ni sidecars.
- **Autenticación CLI/server:** loopback smoke aceptó pairing de dos clientes, lecturas protegidas, logout/revocación y el 401 posterior del token revocado; el archivo Unix fue mode 0600. El server rechaza bind no-loopback, así que este smoke no acredita despliegue LAN/HTTPS ni pairing en servicio no interactivo. El browser mantiene el bearer en memoria y vuelve al overlay al recibir 401; nativo/browser compilan, sin aceptación visual. CLI logout elimina su archivo local aunque no pueda confirmar revocación; el fallo remoto puede dejar la sesión activa hasta expirar. Evidencia: [session/auth CLI smoke](runtime-evidence/2026-11-21-session-auth-cli-smoke.md).
- **D25 recuperación y resincronización:** el coordinador ahora convierte jobs Running recuperados a Paused, valida que cursor/snapshot/IDs coincidan, re-resuelve las fuentes autorizadas antes de Start/Resume y rechaza planes si cambió el conjunto u orden de fotos. Los smokes manuales confirmaron HTTP 422 `invalid_plan` para Start tras cambiar 1→2 fotos y para Resume tras restart, pausa en 1/40 y cambio 40→41. En desktop/browser, los errores transitorios conservan el ID, ocultan controles mientras reconsulta el mismo job cada 2 s y no reenvían acciones cuyo resultado es incierto. Checks server/CLI/Slint nativo y WASM pasaron tras el cambio. Falta aceptación visual/browser/native de los controles y reconexión.
- **D25/D27/CLI/D38/D28:** D25 se monta en el runtime persistente cuando hay raíces autorizadas; la UI sondea trabajos activos cada 2 s y ofrece pausa/reanudación/cancelación. Un endpoint autenticado descubre el job activo persistido al abrir Processing, y los smokes API aceptaron ejecución 2/2 y rechazo de Start/Resume ante un plan obsoleto. Los controles y la reconexión Slint aún no tienen aceptación runtime. D27 fue una revisión estática de lectura paginada; el CLI cubre rutas de catálogo además de pairing y logout autenticados. D38 tiene aceptación runtime limitada del API: guardado CAS, conflicto 409, undo/redo y persistencia tras reinicio sobre el fixture sintético; el panel de receta sigue sin aceptación UI. D28 añade GET JPEG, caché acotada y consumo del cliente por la galería; un preview sintético funcionó tras reinicio. Siguen sin soporte RAW embebido/pareado ni preview antes/después de receta. Export dispone de writer y contrato HTTP no montado. La evidencia sigue limitada a fixtures; falta aceptación UI/multiplataforma. `cargo fmt --all --check` todavía reporta formato en el workspace, incluido el módulo CLI modificado.
- **Pendiente de validación:** tests de `photo-culler-slint`, suite completa del workspace y CI multiplataforma del SHA candidato. No convertir los cambios de código ni los módulos presentes en porcentajes de producto listo.

## Gate de integración

El gate siguiente es una aceptación repetible del SHA candidato exacto en desktop macOS/Linux/Windows, WASM Chromium/Firefox y API/catálogo: import estimate/start, browse de páginas múltiples, decisiones persistidas, errores/retry, move/duplicate/path reuse, scans parciales/excludes, restart y restore. Registrar outputs, artefactos, checksums, catálogo fixture y resultado de integridad en [BUILDS.md](BUILDS.md). Hasta que ese gate pase y las capas pendientes cierren su alcance, este ledger clasifica el proyecto como **candidato de integración**, no producto Rust terminado.
